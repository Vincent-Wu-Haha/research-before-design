# 调研与比较方法

需要制定搜索策略、检查来源或开展复杂比较时读取；不必为每个小问题加载。

## 搜索覆盖

从需求与机制开始搜索，避免只搜索自己偏爱的产品。先广搜得到路线，再查官方资料和实现细节，最后补查风险。时间窗口随领域变化，成熟的基础方法可以较早；“最新”结论必须带检索截止日，不能宣称穷尽全网。

| 方向 | 可采用的查询方式 | 应读取的内容 |
| --- | --- | --- |
| 主流成熟路线 | 问题术语 + architecture / production / reference implementation | 官方文档、实现说明、具体案例及其适用规模 |
| 近期进展 | 问题术语 + recent advances / release / changelog + 合适年份 | 正式发布记录、迁移说明；区分预告与可用版本 |
| 开源实现 | 需求 + open source；GitHub 仓库检索 | README、LICENSE、发布记录、关键配置/代码、相关 issue |
| 学术路线 | 机制术语 + survey / paper / benchmark | 论文相关章节、实验设置、代码、局限及复现情况 |
| 反证 | 候选 + limitations / failure / migration / incident | 已知限制、维护者回应、事故条件、替代方案 |

不固定最低链接数；覆盖决策问题比堆链接更重要。通常先找到不同路线，再为真正可行的候选深化取证。厂商材料可证明其文档声明，不能自动视为独立性能验证。

## 证据记录

长任务保留简短证据表；短任务可内联。若写入文件，使用当前项目允许的位置，不强制创建额外报告。

| ID | 来源与可定位章节 | 读取日期 | 版本/发布日期 | 支持的具体主张 | 类型与局限 |
| --- | --- | --- | --- | --- | --- |
| E1 | 原始 URL、章节/文件路径 | YYYY-MM-DD | 已核实版本，未知则说明 | 只记录实际读取内容支持的事实 | 官方声明/独立测试/论文/推断；环境与缺口 |

对决定性且容易争议的事实，尽量交叉核对独立来源或本地实测。同一论文的摘要、博客和转载不算三份独立证据。无法交叉核对时下调信心并写明原因。自己的综合设计不必伪装成“已有案例”，明确注明推断及依赖证据。

## 可行性与成本

先剔除不满足必须条件的候选，但区分“已证实不满足”和“尚未核实”。对未知项安排验证，不提前判死刑。

按需求选择比较维度：功能匹配、成熟度、性能及测试口径、可扩展性、现有环境兼容、部署和运维、许可、安全/隐私要求、锁定风险、迁移和退出、开发与长期总成本。业务/产品方案使用相应的渠道、组织、试点和执行成本维度，无须强套软件架构。

估算可拆成：调研验证、接入/开发、迁移、测试、部署、运维准备。给区间与范围假设，说明可并行项、外部等待和高不确定项。除非有实测，不把厂商性能或研究实验直接当成用户工作负载表现。

## 借鉴其他方案的准入问题

1. 主体方案缺少哪项必须能力？
2. 新组件的增益有什么证据？
3. 接口、版本、许可、数据一致性与故障语义是否兼容？
4. 新增测试、运维与升级成本由谁承担？
5. 去掉它，最小版本是否仍能达标？

回答不清时，先保持主体方案简单，把组合放入后续验证。
